# 当前已知问题

这份文档是“仓库维护视角”的已知问题，不是外部演示文案。

## 1. `app/services.py` 仍然过重

当前很多业务流程集中在 `app/services.py`：

- 上传处理
- 文件库视图
- 历史视图
- 累计有效内容构建
- PDF 数据准备

这会带来两个风险：

- 后续继续改功能时，很容易在同一文件里堆逻辑
- 审查和定位问题的成本较高

## 2. 解析与展示仍然有较强耦合

当前 `parsers.py`、`rendering.py`、`services.py` 之间仍然有较多结构耦合。

表现为：

- 解析输出结构一旦变化，页面和 PDF 都可能连带受影响
- 某些 section 的展示规则还没完全抽象成独立策略层

## 3. 访问控制还是轻量访问码，不是正式账号体系

现在的访问控制已经能满足：

- 区分 `viewer / admin`
- 创建、停用、删除访问资格

但它还不是：

- 员工账号体系
- 多人协作后台
- 生产级公网登录系统

## 4. 本地数据与仓库边界已经明确，但仍需执行纪律

虽然 `.gitignore` 已经补齐，但如果后续有人手动强制提交，仍然可能把这些本地资料带进 Git：

- 数据库
- 原始底稿
- 核验报告
- 本地导出 PDF
- 本地迁移报告

所以仓库能否长期保持干净，仍取决于后续提交习惯。

## 5. 旧审查材料和新维护文档存在并行

当前项目里有两套文档角色：

- `docs/` 下的新维护文档
- `docs/review/` 下的既有审查材料

这不是 bug，但如果后续不做文档治理，可能出现“维护者不知道先看哪份”的问题。

## 6. 当前目录外还存在一个完整复制包

在上一级工作目录中，还保留着：

- `情报浏览系统_整理导出版_20260415`

它适合外发，不适合继续作为主开发目录。

建议：

- 继续把 `沉香行业情报浏览系统_1.0` 作为唯一主工程目录
- 复制包只作为外部移交件保留

## 7. 当前仍未初始化正式 Git 历史

这轮工作已经把仓库基础文件补齐，但还没有替你做：

- `git init`
- 第一次规范提交
- 发布分支策略
- Issue / PR 规范

这一步建议等你确认目录整理方案后再做。
