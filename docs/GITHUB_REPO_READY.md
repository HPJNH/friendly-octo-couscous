# GitHub 仓库整理说明

## 1. 当前目录最乱的地方在哪里

### 最乱的地方 1：源码工程和运行产物长期混住

具体表现：

- 数据库在项目目录里持续增长
- 文件库会不断累积底稿、简报和历史版本
- 导出 PDF 和迁移报告会不断增加
- 解析快照会随着每次上传持续增长

这类内容本身不是错，但如果不明确边界，就会把“可维护仓库”拖回“本地工作堆”。

### 最乱的地方 2：维护文档和导出文档角色容易混

之前生成的代码汇总、项目总说明属于“导出物”，不应和长期维护文档放在同一层逻辑里。

这轮已经做的处理：

- 长期维护文档放在 `docs/`
- 导出型审查包放到 `exports/review_packages/`

### 最乱的地方 3：上级工作目录里还有一个完整复制包

当前上级目录同时存在：

- `沉香行业情报浏览系统_1.0`
- `情报浏览系统_整理导出版_20260415`

对于 Git 仓库来说，前者应该是主工程，后者只是外发副本。

## 2. 我这次准备怎么整理

这次先做“仓库工程化”，不做外部脚本接入。

### 已做

- 补 `.gitignore`
- 增加 `config/local_settings.example.json`
- 把维护文档和导出文档分层
- 重写 README 为仓库入口说明
- 新增项目结构、运行说明、已知问题、仓库整理说明

### 暂时不做

- 不引入外部 GitHub repo
- 不做云部署
- 不强行删除证据原件
- 不替你直接初始化远程仓库

## 3. 哪些文件建议保留

建议保留并作为仓库主干：

- `app/`
- `config/local_settings.example.json`
- `docs/`
- `deploy/`
- `scripts/`
- `tests/`
- `README.md`
- `requirements.txt`
- `run.py`
- `启动程序.bat`
- `安装依赖.bat`

## 4. 哪些文件建议归档

建议继续本地保留，但不要当成主开发材料：

- `archive/legacy_docs/`
- `archive/duplicates/`
- `docs/review/` 中的历史审查包
- `exports/review_packages/` 中的导出审查文档

这些都属于“有参考价值，但不是主代码”的材料。

## 5. 哪些文件建议删除

### 可以删除的

- `__pycache__/`
- 各类 `.pyc`
- 明确无用的临时缓存
- 空导出目录中的残留测试文件

### 暂不建议粗暴删除的

- 原始底稿
- 原始简报
- 带链接文档
- 复查结果
- 核验报告
- 数据库

这些更适合：

- 本地保留
- 不进 Git
- 需要时再做单独归档

## 6. 当前仓库适合怎么接手

建议后续按这条路径继续：

1. 先把 `沉香行业情报浏览系统_1.0` 作为唯一主工程目录
2. 确认 `.gitignore` 策略
3. 再决定是否执行 `git init`
4. 再做第一次干净提交
5. 然后再进入下一轮功能开发

## 7. 我建议的下一步

在你确认这轮目录整理方案后，下一步最合理的是：

1. 初始化本地 Git 仓库
2. 检查哪些文件应当首次提交
3. 形成第一版干净提交
4. 再继续做功能修改
