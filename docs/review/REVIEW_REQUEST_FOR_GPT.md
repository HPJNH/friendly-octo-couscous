# 给另一个 GPT / 审查模型的说明

你将审查一个本地网页项目，项目名称是：

`沉香行业情报浏览系统_1.0`

请把它理解为一个“本地情报浏览器”，而不是爬虫、自动分析器或自动写稿器。

## 1. 项目是什么

这个项目的作用是：

- 接收两类本地文件
  - 《沉香行业情报研究底稿》
  - 《每日分析简报》
- 自动识别文件类型
- 自动解析 docx/md/txt/pdf 内容
- 把研究底稿拆成 10 个正式板块
- 在浏览器中展示
- 保存历史
- 导出当日 PDF 成果

项目使用场景是：

1. 用户每天上传一份底稿和一份简报
2. 老板打开本地网页先看简报
3. 再按板块浏览底稿
4. 如有需要，再导出 PDF 发给别人看

## 2. 当前目标是什么

当前不是让你继续大规模重构，而是请你独立审查：

- 现有实现是否清楚
- 现有结构是否合理
- 现有问题是否被诚实暴露
- 还有哪些高优先级缺陷没有解决

换句话说，你的任务更接近：

“代码审查 + 产品审查 + 可迁移性审查”

## 3. 你应该重点审查什么

请优先审查下面六个方向：

### A. section 切分是否真的稳

重点看：

- 研究底稿 10 个一级 section 是否只由正式标题切分
- `2.1 / 3.1.1` 这类小节是否不会误伤一级边界
- 当一级标题缺失或写法变化时，系统是否容易重新串栏

### B. 页面是否严格绑定正确 section

重点看：

- section 页是否只读取当前 `section_key`
- 空 section 是否会 fallback 到别的 section
- 详情页和首页卡片是否可能因为业务层取数错误而串栏

### C. 表格解析是否可靠

重点看：

- docx 表格是否保留了行列关系
- 复杂表格、合并单元格、多行表头是否有风险
- 网页表格和 PDF 表格是否足够适合阅读

### D. 历史记录与状态判断是否合理

重点看：

- `新增 / 更新 / 历史保留 / 无内容` 的判断逻辑是否足够可靠
- 当前“历史保留”状态和正文展示之间是否存在冲突
- 多次重复上传后，历史管理是否会失控

### E. 迁移到另一台电脑是否稳

重点看：

- 数据库存绝对路径是否是问题
- 复制整个项目目录后是否能直接继续使用
- 哪些地方仍然绑定当前电脑环境

### F. PDF 导出是否适合作为成果展示

重点看：

- 当前 PDF 是不是足够结构化
- 是否只是粗糙网页打印
- 是否已经达到“给老板或外部人员看成果”的最低标准

## 4. 你应该重点查看哪些文件

建议优先查看：

1. `app/parsers.py`
2. `app/services.py`
3. `app/rendering.py`
4. `app/pdf_export.py`
5. `app/routes.py`
6. `app/db.py`
7. `app/constants.py`
8. `app/templates/day.html`
9. `app/templates/section_detail.html`
10. `app/static/css/style.css`

## 5. 希望你从哪些角度给建议

请尽量从下面几个角度分别给建议，而不是只泛泛说“可以优化”：

### 代码层

- 哪个文件职责过重
- 哪些函数最值得拆分
- 哪些逻辑最容易回归

### 解析层

- section 切分是否还有隐患
- 表格解析是否会在真实文档里失稳
- 标题识别规则是否应该进一步加强

### 数据层

- 当前数据库设计是否足够支撑长期使用
- 历史版本机制是否合理
- 是否应该改掉绝对路径存储

### 页面层

- 哪些页面已经可用
- 哪些页面仍然像调试工具
- 老板视角最该优化哪里

### 导出层

- 当前 PDF 是否适合对外展示
- 需要改成更接近网页，还是保持结构化 PDF 路线

## 6. 你输出建议时的优先级

请优先输出：

1. 严重 bug
2. 结构性风险
3. 高优先级的可用性问题
4. 中低优先级的体验优化建议

如果没有发现严重 bug，也请明确说明“目前最主要的问题已经从 bug 变成架构 / 体验 / 迁移问题”。
